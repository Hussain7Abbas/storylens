# Backend API

[Documentation index](intro.md) · [Development](development.md)

`apps/backend` is a Bun and Elysia service backed by PostgreSQL through Prisma. `src/main.ts` syncs permissions from the routes (see below) and starts the app defined in `src/server.ts`, which mounts plugins, `/health`, Better Auth at `/auth/*`, the reader API at `/api/user` (`src/routes/user.ts`) and the dashboard API at `/api/admin` (`src/routes/admin/`). `src/setup.ts` supplies the Prisma client, current authenticated user, and an English/Arabic translation helper to route context.

## Main areas

- `src/routes/` handles reader accounts (`accounts.ts`), novels (including an optional `context` text that the extension's AI features use as the novel's global background), chapters, keywords and their aliases/versions, replacements, categories and natures (each with an optional `description` that tells the extension's AI keyword suggestion when to choose it), website selectors and biases, uploads, and AI operations. `src/routes/admin/` holds the dashboard API: sign-in, overview stats, users, roles, permissions, novels (with `GET /novels/:id/keywords`, every keyword of a novel with its versions, aliases, category, nature, image and creator), keywords (list, create with a base version at chapter 0, rename and matching, delete, link/alias/version merges), keyword aliases and versions (`/keyword-aliases`, `/keyword-versions`: create, update, delete; a new version must start after the latest one and closes it, and the base version can't be deleted), category and nature lists, configs and image upload. Version range edits reject overlap, moving a version's start updates the preceding end, and deleting a later version extends the preceding range. Folding a keyword into a version also closes the preceding range. Shared admin keyword response shapes live in `src/schemas/admin-keywords.ts`.
- `src/middleware/authorize.ts` defines `authorize(portal)`, which checks the session's portal, the account's access to it and the route permission, plus `canModerate` and ownership checks. `src/lib/permissions/` holds the permission catalog and route sync.
- `src/lib/auth/` combines Better Auth with bearer session handling; `src/lib/db/` supplies Prisma, `src/lib/storage/` handles image storage, and `src/lib/ai/` supports the backend OpenRouter chapter-selector detector used when the extension has no configured desktop AI provider.
- `prisma/schema.prisma` defines users (with `isUser`/`userRoleId`, `isAdmin`/`adminRoleId` and `isGuest`), sessions (with the `portal` they were issued for), roles, permissions, sessions, novels, chapters, keywords, aliases, versions, replacements, selectors, and related records. `prisma/migrations/` tracks schema changes; `prisma/seed/` populates development data, storing each seeded keyword's description, category and nature in its chapter-zero version.

Novel and keyword text is translated per language: novels have `nameAr`/`nameEn` and `descriptionAr`/`descriptionEn`, keywords have `nameAr`/`nameEn`, and at least one name is required (each is unique per language: novels globally, keywords per novel). Stored text is plain: the API trims input but does not HTML-escape it (migration `store_raw_text` decoded rows written before; literal entity sequences in old data are ambiguous and require a source-data audit before rollout), and no client may insert it as HTML (`test/stored-text.test.ts` scans the extension, dashboard and website). The reader API reads the request language from `Accept-Language` (`ar…` is Arabic, anything else English; `setup.ts` exposes it as `lang`) and lists and searches only novels and keywords named in it; a `name` sort column sorts by that language's field. Reader writes accept either name; `POST /api/user/novels` with a slug an existing novel already has fills that novel's missing translation instead of creating a duplicate, and readers may add a missing name translation with `PUT /api/user/novels/:id`. Helpers live in `src/utils/translation.ts`. The dashboard edits both languages, and `src/routes/admin/keywords.ts` backs its Match translations page: `GET /api/admin/keywords/` (by novel, `search`, `missing`/`has` language, or `untranslated=true` for keywords named in exactly one language), `PUT /:id` (set names), and `POST /:id/link` (merge a keyword into its other-language counterpart), `/:id/alias` and `/:id/version` (fold a keyword into another as an alias or a new version; versions have no name, so the folded names also become aliases). `POST /:id/link-alias` (`{ aliasId }`) links a keyword named in one language to an alias of another keyword instead: the keyword's name (its language read from its script) becomes that alias's name in the other language, the alias takes the keyword's image, category and nature where it has none (and where both have one, the more recently updated record wins), and the keyword is merged away; it is refused when the alias already has a different name in that language. Merges move aliases, chapter links and replacements to the target. Distinct aliases stay distinct even when one name matches another alias's translation; same-name aliases combine compatible translations, while a distinct conflicting translation becomes a separate alias when possible. Linking to an alias is serialized per alias, and refuses a source with later versions because deleting it would erase that history.

Aliases are named by `nameAr`/`nameEn` like keywords, at least one of them, each unique per keyword (migration `alias_names_only` filled the columns from the old `name` by script, put names without letters in every language the keyword is named in, stopped with a list on names that would collide, and dropped `name`). Reader and dashboard alias routes take the language fields directly. Version, chapter and replacement text is not translated yet.

`Novel.context` is accepted on `POST /api/user/novels` and `PUT /api/user/novels/:id` (and the dashboard's novel routes), and `PUT /api/user/novels/:id/context` sets it alone (up to 20,000 characters, stored as typed like other text). Moderators (`user:moderate`) and the dashboard can always change it; readers can write it only while it is empty, which is how the extension saves the context its AI researched on first use. Character images generated or picked in the extension upload through `POST /api/user/files/upload` to imgbb (`STORAGE_IMGBB_API_KEY`); the multipart form carries the client's file `id`, so a resend of a stored upload returns it without uploading again (another user's ID is 409 `ID_CONFLICT`). Concurrent sends of one ID hold an advisory lock before calling the provider. A provider success followed by a backend crash before the database commit can still leave an orphaned remote file; the provider does not offer an atomic transaction with PostgreSQL.

The server centralizes expected HTTP errors with `HttpError` and `AuthError`. Routes validate inputs with Elysia schemas and use Prisma for persistence. The development OpenAPI UI is at `/docs`, with `/openapi.json` feeding the extension's and dashboard's Orval clients (the extension excludes `Admin: …` tags; the dashboard generates only them). The OpenAPI plugin returns 404 in production mode.

Environment variables are validated in `src/env.ts`. Copy `.env.example` and supply a database URL, Better Auth secret, and storage key. `BETTER_AUTH_URL` must be the API's public origin and `WEBSITE_URL` the website origin (default `https://storylens.iscoded.com`); `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` enable Google sign-in; `RESEND_API_KEY` and `EMAIL_FROM` (a sender on a Resend-verified domain) deliver registration codes; the seed needs `DASHBOARD_ADMIN_EMAIL`, `DASHBOARD_ADMIN_USERNAME` and `DASHBOARD_ADMIN_PASSWORD`; AI features need their values. `PORT` defaults to 3000. The local Docker database is defined by `docker-compose.yml`.

## Sync API

The extension's offline engine writes keywords, aliases, versions, replacements, categories and natures through the reader routes under this contract (protocol version 2, `GET /api/user/sync/protocol` → `{ version: 2 }`; older APIs answer 404):

- **Client IDs.** Creates require `id` (a UUID; `POST /keywords` also requires `versionId`, its base version's ID). A create whose row already exists with the same creator and parent (novel or keyword) is a replay: it returns the stored row in the route's 200 shape and skips every side effect (base version, version auto-close, replacement chain rewrite). Another owner or parent is 409 `ID_CONFLICT`; categories and natures replay when names and color match. Two identical replays at once return the same row (`src/lib/sync/replay.ts`).
- **Stale writes.** Updates require `baseUpdatedAt` (the row's `updatedAt` the client edited from). When the stored revision differs, the route answers 409 `{ message, code: "STALE_WRITE", current }`, `current` in the route's 200 shape. Every synced `PUT` checks 404, then ownership (403), then staleness, then rules and duplicates, then atomically compares the revision at write time. A database trigger advances `updatedAt` by at least one millisecond on every update, including dashboard and bulk writes. Deletes are unconditional (a delete wins).
- **Partial updates and clears.** Every synced `PUT` changes only the sent fields (`PUT /replacements/:id` validates the stored row merged with them); `null` clears an alias's or version's `description` and `imageId`.
- **Error codes.** Every synced error carries `code` (`src/lib/sync/error-codes.ts`, a contract with the extension): `NOT_FOUND` and `PARENT_NOT_FOUND` (404), `NOT_OWNER` (403), `STALE_WRITE`, `ID_CONFLICT`, `KEYWORD_NAME_TAKEN`, `ALIAS_NAME_TAKEN`, `REPLACEMENT_EXISTS`, `LOOKUP_NAME_TAKEN` and `UNIQUE_VIOLATION` (409; Prisma `P2002` maps to it globally, `P2025` to 404 `NOT_FOUND`), `NAME_REQUIRED` (422), `REPLACEMENT_BIDIRECTIONAL`, `VERSION_CHAPTER_REQUIRED`, `VERSION_NOT_AFTER_LATEST`, `VERSION_ONLY_PROTECTED`, `VERSION_BASE_PROTECTED`, `CATEGORY_IN_USE`, `NATURE_IN_USE` (400) and `CURSOR_EXPIRED` (410). `HttpError` takes the code as `code` and stores it as `errorCode` (Elysia reads an error's own `code` as its error type).
- **Edit rights.** Alias and version edits and deletes are allowed to a moderator, the row's own creator or the parent keyword's creator (`assertOwnsAnyOf`, decision D12). Category and nature names are checked per language they are given in, and blank names are stored as `null`; deleting one used by a version or an alias is refused.
- **Change feeds.** Postgres triggers (migration `sync_change_feed`) record every insert, update and delete of novels, keywords, aliases, versions, replacements, chapter biases, categories and natures in `SyncChange` (`seq` order), so route writes, dashboard merges, cascades and bulk updates all appear. `GET /api/user/sync/novels/:id/changes`, `/sync/lookups/changes` and `/sync/catalogue/changes` take `since` (a cursor) and `limit` (at most 1000) and return the current rows of changed IDs in both languages, `deleted: [{ entity, id }]`, the next `cursor` and `hasMore`; without `since` they return only the cursor a full pull starts from. Migration `sync_commit_order_and_revisions` serializes feed inserts with a transaction-scoped advisory lock, so a higher sequence cannot commit before a lower one. Full pulls use `/sync/snapshot/novels/:id`, `/sync/snapshot/lookups` and `/sync/snapshot/catalogue`; each returns complete rows and a cursor from one repeatable-read transaction, avoiding skips when rows are deleted during offset pagination. The `sync-feed-pruner` cron deletes rows older than 90 days (keeping the newest); an older cursor answers 410 `CURSOR_EXPIRED` and the client pulls in full. Logic lives in `src/lib/sync/feed.ts` and `src/routes/sync.ts`.

`test/sync-api.test.ts`, `test/sync-feed.test.ts`, `test/sync-files.test.ts` and `test/sync-migrations.test.ts` exercise this against a real database: `make test-live` migrates `TEST_DATABASE_URL` (a disposable database) and runs the suite with them; plain `bun run test` skips them.

## Compatibility

Installed extensions and desktop clients lag behind the API, so changes follow [API and data compatibility](compatibility.md). `src/plugins/client-version.ts` answers 426 Upgrade Required to `/api/*` requests whose `X-Client-Version` is older than `MIN_CLIENT_VERSIONS` (`src/lib/compat/client-version.ts`). The `deprecated` route option (`src/plugins/deprecation.ts`, available through `setup`) and `deprecate()` (`src/lib/compat/deprecation.ts`) mark deprecations in OpenAPI and send `Deprecation`/`Sunset` headers, which CORS exposes to browsers. `test/deprecations.test.ts` fails once a removal date passes, and `make deprecations` lists them all.

## Health checks

`GET /health` is a public liveness check that returns `{ status: "ok", timestamp }`. `GET /health/ready` is a public readiness check. It reports `backend` (with uptime), `database`, and `chromeStore`, each with a `status` and `latencyMs`, plus `versions.review` (the pending `Review_Version`, or `null`) and `versions.store` (the published Chrome Web Store version). Each check times out after 5 seconds.

The overall status is `down` with HTTP 503 when the database check fails. It is `degraded` with HTTP 200 when the store check fails or `CHROME_EXTENSION_ID` is unset, and `ok` otherwise. Failure details are logged on the server, not returned. Logic lives in `src/lib/health.ts` and the routes in `src/routes/health.ts`.

## Deployment and review version

Production runs under PM2 and deploys with `make sync`, which stops the API, pulls, installs dependencies, generates the Prisma client, applies migrations, builds, and restarts. `make pm2-start`, `pm2-stop`, `pm2-restart`, and `pm2-delete` manage the process.

Backend deploys wait for the matching extension release. After a store submission, the extension's publish workflow dispatches `extension-submitted` to the backend repository. The backend's `set-review-version.yml` workflow then runs `make set-review-version VERSION=x.y.z` on the server over SSH, which upserts the `Review_Version` config through `src/scripts/set_review_version.ts`. That job uses the backend repository's `production` environment secrets `DEPLOY_SSH_HOST`, `DEPLOY_SSH_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_SSH_PASSPHRASE` (the key's passphrase), optional `DEPLOY_SSH_PORT` (default 22), and `BACKEND_PATH`. In production, the `review-version-watcher` cron (every 10 minutes) compares that value with the version the public Chrome update endpoint reports for `CHROME_EXTENSION_ID`. When they match, it deletes the config and starts `make sync` outside the PM2 process tree, logging to `sync.log`. Without `CHROME_EXTENSION_ID`, the cron logs a warning and leaves the config in place.

For local API and database commands, see [Development](development.md) and the [backend instructions](../apps/backend/AGENTS.md). The [backend README](../apps/backend/README.md) has standalone setup details.

## Portals, roles and permissions

There are two **portals**: `user` is the reader API (`/api/user`: extension, website account pages, desktop client) and `admin` is the [dashboard](dashboard.md) API (`/api/admin`). One account (one email, username and password) can use either or both: `isUser` with a reader role in `userRoleId`, and `isAdmin` with a dashboard role in `adminRoleId`. Each login route issues a session for its own portal (`Session.portal`) and refuses accounts without that access. `authorize(portal)` answers 403 when the session was issued for the other portal or the account has since lost access, so a reader token (which the extension shares with the website and desktop client) never opens the dashboard. `isGuest` marks anonymous extension installs; verified registration or Google sign-in clears it.

Each portal's role holds **permissions**, and a request only sees the role of its session's portal. A permission's key is the route's method and template, e.g. `GET /api/user/novels/:id`, so every endpoint has its own permission. `syncPermissions()` runs at startup: it creates a row for every non-public `/api/{portal}` route (descriptions come from the route's `detail.summary` for dashboard routes and `USER_ENDPOINT_DESCRIPTIONS` for reader routes), deletes rows for removed routes, and gives new permissions to the system roles by default. Dashboard edits to existing grants are kept. `user:moderate` is a capability, not an endpoint: it lets reader-portal routes edit other readers' content, set version chapter ranges, rename novels and replace a filled novel context (`canModerate`).

System roles are created by migration `20260928201239_add_portals_roles_permissions`, which also mapped the old enum (guest → Guest, user → Reader, admin → Moderator, all with reader access). Migration `20260929090000_split_user_portal_access` then replaced `User.portal`/`roleId` with the two access pairs and gave existing sessions their portal:

| Role | Portal | Default permissions |
| --- | --- | --- |
| Super Admin (`super-admin`) | admin | Every dashboard permission, re-granted on each startup; read-only in the dashboard |
| Guest (`guest`) | user | Reader-API reads plus profile, sign-out and AI selector detection |
| Reader (`reader`) | user | Guest permissions plus writes to own keywords, aliases, versions and replacements, novel creation, uploads and credential changes |
| Moderator (`moderator`) | user | Every reader permission plus `user:moderate` and catalogue management (categories, natures, chapters, selectors, biases, novel deletion) |

Public endpoints (`PUBLIC_ENDPOINTS` in `src/lib/permissions/catalog.ts`): reader guest creation, registration and verification, login, providers and OAuth session exchange, and dashboard login. Dashboard access is never self-registered: `POST`/`PUT /api/admin/users` grant it, and the seed (or `make seed-dashboard-admin`) gives `DASHBOARD_ADMIN_EMAIL` the super-admin role. An existing account with that email keeps its password and reader access; otherwise a dashboard-only account is created (and reset on later runs). Every account needs at least one access, each with a role of its portal. The dashboard API refuses to change the caller's own dashboard access or role, delete the caller, or remove the last super admin; roles in use or marked system can't be deleted. Changing a password signs the account out everywhere, since both portals share it.

Reader login, registration and the OAuth exchange live under `/api/user/auth` and are public because the website's account pages call them with no session after sign-out. Register still upgrades the guest in place when a guest bearer token is sent. The CORS plugin reflects requested headers (`allowedHeaders: true`), since a literal `*` never covers `Authorization` for the website's cross-origin calls.

## Email verification (registration)

Email/password registration takes two requests. `POST /api/user/auth/register` validates the details, rejects a taken email or username, and stores a pending registration in Better Auth's `verification` table (identifier `register:<email>`; the value holds the bcrypt password hash and an HMAC of the code keyed by `BETTER_AUTH_SECRET`, never the code or password). It emails a six-digit code through Resend (`src/lib/email/`, template in `src/lib/auth/registration.ts`, localized by `Accept-Language`) and returns `{ email, expiresAt, resendAfterSeconds }` with no session. Codes expire after 10 minutes; calling `/api/user/auth/register` again for the same email replaces the code but returns 429 within the 60-second cooldown. A failed send returns 502 and discards the pending row so the reader can retry at once.

`POST /api/user/auth/register/verify` takes `{ email, code }`. Five wrong codes void the pending registration; a matching code is claimed once (deleted with a compare-and-delete), availability is rechecked, and the account is created, or the guest named by the bearer token is upgraded in place, with `emailVerified: true`. It returns `{ user, token }` like login. Without `RESEND_API_KEY`/`EMAIL_FROM`, development and test print the email to the console; production returns 502. There is no global per-IP rate limit on sending, only the per-email cooldown.

## Google sign-in (OAuth)

Better Auth (`src/lib/auth/index.ts`) serves only OAuth. Its handler stays at `basePath: '/auth'` through the `/auth/*` catch-all in `src/routes/better-auth.ts`, outside `/api`, so the Google redirect URI is unchanged. It is unguarded because OAuth starts signed out. Better Auth's email/password, `update-user`, email, password, delete, and account-linking endpoints are listed in `disabledPaths`, and `username`, `portal`, `isGuest`, `roleId`, and `password` are `input: false`, so request bodies can never set them. Custom routes remain the only credential and profile path.

Google turns on when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set; `GET /api/user/auth/providers` reports `{ google }` so the website shows the button without a rebuild. Register `{BETTER_AUTH_URL}/auth/callback/google` (production: `https://storylens-api.iscoded.com/auth/callback/google`) as the authorized redirect URI in Google Cloud, and add `https://storylens.iscoded.com` as an authorized JavaScript origin. `trustedOrigins` contains `WEBSITE_URL`, so callbacks can only return to the website.

The flow: the website calls `POST /auth/sign-in/social`; Google returns to the API callback, which creates or finds the user and sets a Better Auth session cookie on the API domain. It then redirects to the website's `/profile/oauth/` page, which calls `POST /api/user/auth/oauth/session` with that cookie. Dashboard accounts are refused there. That route issues a bearer session for the extension and signs the cookie session out. If the page also sends a guest token from the same browser, `mergeGuestInto()` moves the guest's novels, keywords, aliases, versions, replacements, and files to the account and deletes the guest; registered users are never merged. The user-create hook gives OAuth sign-ups the reader portal and `reader` role, a username derived from the display name (not the email), and a random bcrypt password so the credential routes stay consistent. `User.image` stores the provider picture URL. Google accounts whose verified email matches an existing account link to it, per Better Auth's defaults.

Reader password and email changes are two-step, like registration, and reject guests. `POST /api/user/auth/change-password` accepts `currentPassword` and `newPassword`, verifies the current credential, validates the new password at 8–72 characters, and emails a six-digit code to the account address; `POST /api/user/auth/change-password/verify` accepts `{ code }` and atomically updates both the user password and credential account hash. `POST /api/user/auth/change-email` accepts a new `email`, rejects the current or another account's address, and emails the code to the new address; `POST /api/user/auth/change-email/verify` rechecks availability, updates `User.email` (marked verified) and the credential account ID in one transaction, returns the updated user, and sends a notice to the previous address. `src/lib/auth/account-change.ts` stores each pending change in the `verification` table (`change-password:<userId>` or `change-email:<userId>`) with an HMAC of the code and the same 10-minute expiry, 60-second resend cooldown, and five-attempt limit as registration; a code for one kind cannot confirm the other. Existing sessions remain valid. Dashboard users change their password with `PUT /api/admin/auth/password`, which checks the current password (no email flow) and signs out the account's other sessions; the password is shared with reader access. Backend tests cover these flows, guards, and validation, plus session-less sign-in, two-step registration (code delivery, expiry, attempt limit, single use, resend cooldown, failed delivery), the OAuth exchange, guest merging, route precedence, and OAuth usernames, with isolated database mocks. `test/permissions.test.ts` checks against the real routes that every endpoint sits under a portal, has a permission and description (or is public), keeps the old default access, and returns 401 without a session; `test/authorize.test.ts` covers the portal, access and permission guard, including accounts with both kinds of access.
