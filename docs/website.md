# Story Lens website

[Documentation index](intro.md) · [Implementation tracker](../website-plan/main.md)

`apps/website` is the independent public `storylens-website` repository, the fourth submodule. Next.js App Router builds English and Arabic landing, privacy, terms, and account (`/profile/`, `/profile/login/`, `/profile/register/`, `/profile/password/`, `/profile/email/`) pages as a static export. Tailwind v4 and CSS tokens implement the Ink & Iris identity: neutral light/dark surfaces, violet primary actions, Inter UI/headings, a serif only for reading passages, and Lucide outline icons at 1.75 stroke weight; GSAP and a lazy Three.js lens are optional. The original demo explains highlights and replacements. The active palette and UI rules live in `apps/website/design-system/MASTER.md`, mirrored by the extension's `src/styles/palette.ts`. The approved Lensbook logo supplies the header, favicon, Apple touch and manifest icons; canonical assets and the palette chart live in [Branding](branding/README.md). Website source and content use PolyForm Noncommercial 1.0.0.

Use Bun and Biome: `make dev-website`, `make build-website`, `make website-typecheck`, `make website-lint`, `make website-test`, `make website-lhci`. Root install/build/typecheck/test include the website. Browser tests run Chromium, Firefox, WebKit and a mobile viewport with axe. Install browser binaries with `bunx playwright install` in the website checkout.

## Account pages

The account pages work on their own, with or without the extension (pricing plan phase 6, decision D13). Password managers recognize the forms through their `autocomplete` hints (`username`, `current-password`, `new-password`, `one-time-code`). `src/components/account/AccountApp.tsx` renders every view on the client from the **website's session**: an HttpOnly cookie on the API (`__Host-sl_web`, 30 days) that JavaScript never reads. `src/lib/account/api.ts` sends those calls with `credentials: "include"` and the `X-Storylens-Web: 1` CSRF header (`GET /api/user/auth/me` tells whether the website is signed in; `/api/user/auth/web/login`, `/register/verify`, `/oauth/session`, `/logout`, `/extension-session`, `/adopt`). Only the Google sign-in start (`/auth/sign-in/social`) goes to Better Auth at `/auth`. The API origin is `NEXT_PUBLIC_API_URL` (default `https://storylens-api.iscoded.com`); `deploy/security-headers.ts` adds it to CSP `connect-src`, so set the same value at build time. Cookies work because the website and API share the `iscoded.com` site.

Signed out, `profile/`, `password/` and `email/` redirect to `login/?next=<page>`; after signing in the reader returns there. `safeNext` (`src/lib/account/reconcile.ts`) accepts only this locale's `/profile/` and `/pricing/` paths. Registration has two steps: the form requests an emailed six-digit code, then the same card asks for it with a resend button that counts down the API's cooldown and a way back to the prefilled form; the details stay only in component memory. If the browser blocks the API cookie, a successful sign-in explains that cookies for the API are needed.

The installed extension is kept on the same account through `src/lib/account/bridge.ts` (a `window.postMessage` protocol answered by the extension's `website-bridge` content script), but it never blocks the page. `decide(web, bridge)` in `reconcile.ts` is a pure function of the two states (unit-tested in `tests/account-reconcile.spec.ts`):

| Website | Extension | The page does |
| --- | --- | --- |
| Signed in as A | Not installed | Shows an install card on the profile (`data-analytics-cta="profile"`) |
| Signed in as A | Signed out | `POST /auth/web/extension-session`, then bridge `set` |
| Signed in as A | Guest | The same, sending the guest token so its data merges into A |
| Signed in as A | A, with an older copy | Bridge `set` with the fresh user and the extension's own token |
| Signed in as A | B | Asks: **Use A in the extension** (hand-off) or **Switch this site to B** (`/auth/web/adopt` with B's token) |
| Signed out | B | `/auth/web/adopt` with B's token: the website signs in as B |
| Signed out | Guest, signed out or none | Sign-in and registration forms |

Each automatic step runs once per state pair, so a failing call cannot loop. Registering from a guest sends the guest token on both requests, so the account keeps the guest's data. **Continue with Google** shows only when `GET /api/user/auth/providers` reports it enabled; `/{locale}/profile/oauth/` exchanges the API's OAuth cookie for the website session and then the profile hands it to the extension (merging its guest). **Sign out** ends the website session and clears the extension when it holds the same account; with another account in the extension only the website signs out, and a `sessionStorage` flag (never a token) stops the page from adopting that account again until the reader signs in. The header shows **Sign in** or the reader's name (icon only on phones) through `src/components/layout/HeaderAccount.tsx`, which caches the display name in `sessionStorage` for five minutes and keeps its width while it loads. The profile shows the localized system role or a custom role's name; users from older extension builds are normalized. Account pages, including `/profile/oauth/`, are `noindex` and absent from the sitemap. `tests/account.spec.ts` mocks the API (with the cookie session held in memory) and stands in for the extension with a fake bridge. For local end-to-end work, build the extension with `WXT_WEBSITE_URL` set to the website's origin and run the API with `WEBSITE_DEV_ORIGINS` (and `WEB_SESSION_INSECURE_COOKIE=true` over plain HTTP).

## Balance and pricing pages

Lenses are the coin for Story Lens Cloud AI ([pricing plan](../pricing-plan/main.md)). **`/{locale}/profile/balance/`** (signed in, `noindex`, `AccountApp view="balance"`, `src/components/billing/BalancePage.tsx`) shows the balance with its dollar value, the reader's requests (status, the contact used, rejection reasons, **Cancel** on pending ones after a confirmation) and the lens history, and holds the **Request lenses** form (`#request`, focused when opened with that hash). The form takes a whole number of lenses within the API's limits (presets from the minimum), a required WhatsApp number or Telegram username/number (`src/lib/billing/contact.ts`, the API's rules; prefilled from the last request) and an optional note; the total is computed in the browser with `priceCents` (`src/lib/billing/money.ts`, integer micro-dollars, the API's half-up vectors). It sends the quoted price string and a client UUID that is reused only after a network error. `PRICE_CHANGED` reloads the price and asks the reader to check the new total; the other billing codes show their limits. There are no payment instructions: the owner contacts the reader on the chosen channel (decision D9). The extension links here with `?need=<n>&feature=<key>&from=extension`, which shows what is missing and preselects an amount that covers it. With no extension answering, the page offers the install.

Gifts and purchases the website has not shown are celebrated on the profile and balance pages (`GiftCelebration.tsx`, `GET /billing/balance?surface=website`): gifts open a dialog (summed, with any gift note) and one short confetti burst from `canvas-confetti`, loaded only when there is a gift and skipped with reduced motion; purchases get a plain notice. They are then marked seen for the website only, so the extension celebrates them separately. A trial of 0 creates no gift, so nothing appears.

Balance snapshots carry their account ID. When the website switches accounts, the previous balance is hidden until the new response arrives, and billing forms/history and gift celebrations remount for that account. The account-choice action clears the old notice. `tests/account.spec.ts` delays the new balance response to check that the old balance never appears under the new profile and that acknowledging one account's gift does not suppress another's. The [local browser rehearsal](lenses-local-e2e.md) also checks the actual extension bridge, cookies and billing workflow against PostgreSQL.

**`/{locale}/pricing/`** is public and indexed (in the sitemap and header, mobile menu and footer navigation; the landing page's companion section links to it). The pricing card reserves its table area during loading and failure to prevent the FAQ jumping in either language. Its copy is static, but every number comes from `GET /api/user/billing/pricing` on each visit (`PricingTable.tsx`): enabled features in order with their lens price (Free for 0) and dollar value, the lens price, the trial (hidden when 0) and the request limits, with a retry when the API is unreachable. Prices are shown only through `LensPrice`/`LensCoin` (`src/components/billing/`), with every Arabic plural form from `Intl.PluralRules` and Latin digits. `tests/billing.spec.ts` and `tests/pricing.spec.ts` cover both pages with a mocked API.

## Analytics

Google Analytics 4 is opt-in and off by default. It is built only when `NEXT_PUBLIC_GA_MEASUREMENT_ID` (a `G-…` ID) is set at build time, for example in the server's ignored `.env`; that also adds the Google tag origins to the generated CSP. Visitors see a bilingual consent banner (`src/components/layout/AnalyticsConsent.tsx`) with equally weighted **Allow analytics** and **No thanks** buttons, and can reopen it from **Analytics settings** in the footer. `src/lib/analytics.ts` loads gtag.js only after consent, keeps Consent Mode ad signals denied, disables Google Signals and ad personalization, and strips query strings and fragments from `page_location`. Events are `install_extension_click` (with `cta_location` from `data-analytics-cta` on Chrome Web Store links) and GA4's recommended `login` and `sign_up` with `method` only. A sent lens request adds `lens_request_submitted` with no parameters. Changing collected data requires updating both privacy MDX files and `design-system/data-inventory.md`. `tests/analytics.spec.ts` runs only against an export built with a measurement ID. The website repository vendors the MIT-licensed `analytics` agent skill in `.claude/skills/analytics` for tracking-plan guidance. The extension has its own optional analytics consent setting and event catalog in `apps/extension/AGENTS.md`.

## Production

Live website: [storylens.iscoded.com](https://storylens.iscoded.com). Cloudflare A record proxies to `178.105.43.174`, created using local `flarectl`. Hosting is the existing `ssh raseen` server. Website code has its own checkout at `/srv/storylens-website` on branch `main`, separate from `/srv/storylens-backend`. There is no Next.js process in production.

Nginx config: `apps/website/deploy/nginx/storylens.iscoded.com.conf`. The server runs `make sync` inside its website checkout to fast-forward main, install pinned dependencies with Bun, build (using the dedicated `/opt/storylens-node/bin` Node LTS runtime for Next.js), generate CSP hashes, create a release, atomically update `/var/www/storylens/current`, test Nginx, and reload. Old releases remain for rollback. Initial HTTPS uses a Let’s Encrypt webroot certificate; port 80 serves challenges and redirects other requests to HTTPS. `/` redirects to `/en/`; explicit locale links preserve paths and hashes. Static assets receive long cache expiry. Build-generated script hashes allow Next bootstrap without unsafe-inline script permission. Inline styles support GSAP/Three.js styles.

There is no CI quality workflow; run typecheck, Biome and browser tests locally. Auto-deploy is activated only with dedicated SSH secrets and `DEPLOY_ENABLED=true`; no personal local key is copied to GitHub. Local static preview uses `make start`. Preview artifacts are not publicly indexed deployments. Website release integration in `.xeploy.json` is separate from a server update; the release merges production main, then configured deployment runs.

Before setting the Google credentials in production, the owner must review a privacy-policy update in both languages: Google sign-in stores the Google account ID, name, email, profile picture URL, and OAuth tokens, and the current statement that Story Lens does not integrate Google user-data APIs would no longer hold. ## Google OAuth domain ownership

Google OAuth homepage verification requires a Search Console **Domain property** for `iscoded.com`, verified by a Google account that owns the Cloud project. Website publication and HTTPS alone do not establish this ownership. A Google-generated TXT record was added through `flarectl` on 2026-09-27; Search Console confirmed “Ownership verified” for the owner-approved Google Cloud Project Owner account. Keep the verification TXT record permanently, alongside the existing mail TXT records.

Use `https://storylens.iscoded.com/en/` as the OAuth homepage and `https://storylens.iscoded.com/en/privacy/` as its matching privacy policy URL; both are public and return 200. The authorized domain is `iscoded.com`. After Google confirms ownership, follow the review team's resubmission instructions. Do not change OAuth redirect URIs as part of domain verification. Enabling Google sign-in itself is covered in the [backend guide](backend.md#google-sign-in-oauth); update the privacy policy before turning it on (see Legal maintenance).

References: [Google domain verification](https://support.google.com/cloud/answer/13804266), [homepage requirements](https://support.google.com/cloud/answer/13807376).

The landing page gallery (`components/sections/ExtensionScreenshots.tsx`) uses twelve actual extension captures in `public/images/extension/`: glossary, full-page form and selection panel, each in English/Arabic and light/dark. They contain isolated sample data and switch with the website theme. Source PNGs and validation notes are in `design-system/validation/ink-iris/`.

Each language has five screenshots covering highlighting, aliases, chapter versions, text replacement, and character editing. Local assets live in `public/images/reading/` (640/1280px WebP) and `public/videos/extension/` (MP4 and WebVTT). The website MP4s use the original recordings without burned-in text; timed WebVTT captions appear at the top center over a dimmed, blurred panel and fade in/out, while reduced-motion visitors see them immediately. Native captions remain available without JavaScript, and a six-step text transcript follows the video. Video uses native controls and loads on demand, with no autoplay or third-party player. Screenshot links open a native dialog with Escape, a close button, and focus return; without JavaScript they open the image directly. Captured extension screens retain their light theme, while the surrounding website follows the selected theme. The hero’s secondary link jumps to the walkthrough. Refresh media from [the Chrome store capture workflow](chrome-store/README.md) and update both languages together. Verification is recorded in `apps/website/design-system/validation/reading-media/README.md`.

`Deploy production` runs on every push to `main` (or by manual dispatch on `main`) and sends the pushed SHA over SSH; the server rebuilds the site. It runs no typecheck, Biome, browser tests or Lighthouse. Release tags do not trigger it; the xeploy publish to `main` does. `production` environment secrets contain the host/user, port, known host key and a dedicated command-restricted SSH key. `DEPLOY_ENABLED=true` enables the workflow. The server command `/usr/local/lib/storylens/ci-ssh.sh` validates main ancestry, refuses dirty checkouts, locks checkout changes, checks out the exact commit, and runs the existing atomic release deployment. Updating that installed wrapper is separate from publishing the website. The workflow takes effect once committed and pushed; local validation does not publish a release.

Lighthouse includes both pricing locales. Against the pre-release production API, expected anonymous `/auth/me` 401 and missing billing 404 responses count as console errors; record that deployment limitation separately from performance/accessibility/SEO and layout budgets.
