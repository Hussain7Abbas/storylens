# Browser extension

[Documentation index](intro.md) · [Development](development.md)

`apps/extension` is a WXT and React extension for Chrome and Firefox. The popup lets readers manage novels, keyword coloring, replacement rules, and settings; its profile button opens the account pages on the website. The content script detects supported pages and applies reading features; the background service worker handles messaging, selector loading, API proxy requests, and synchronization.

The popup opens on **Coloring**. **Settings → AI** holds the desktop client pairing: readers enter the port and pairing token, click **Connect / refresh models**, and choose a discovered Claude/Codex model and effort. Below the pairing it has two editable **AI prompts**, seeded with defaults from `src/lib/desktop-client/ai-prompts.ts` and saved in extension-local storage (`storylens-ai-prompts`): the **Keyword prompt** controls how AI add and chapter extraction write descriptions and pick categories/natures, and the **Image prompt** explains and controls how character images are drawn. **Reset to default** restores a prompt, and an emptied prompt falls back to its default. Each prompt is placed first in its request and marked as taking priority over the chapter text and novel context. The AI actions themselves live on the in-page launcher (below): **Summarize page** captures the active page's body and shows loading, result, or error at its top, and the selection panel's **Use AI** switch suggests the selected entry's details. The background worker contacts the authenticated loopback service. After each successful connection, and whenever the reader signs in or out, it also shares the Story Lens API URL and session token (or `null`) with the client for its [wiki crawler](client.md#wiki-crawling). See the [client guide](client.md) for setup, limits, and privacy behavior.

On a page whose domain has a website selector in the novel-site database or extension cache, a circular logo button on a neutral surface with an iris focus ring appears in the top-right corner by default. Drag it to move it; its position is saved in extension-local storage (`storylens-page-launcher-position`) across sites and reloads. Saved and dragged positions are clamped to the viewport, including after resizing. Within 10 px of the nearest viewport edge, the idle circle tucks against that edge with 3 px visible; moving the pointer within 10 px reveals it at its saved position. Dragging, keyboard focus, and an open popup keep it visible. **Settings → General → In site popup** controls Show/Hide, defaults to Show, and is saved in extension-local storage (`storylens-page-popup-visible`) with immediate updates across tabs. It opens the same extension popup in an overlay iframe; readers can use either this button or the browser toolbar icon. The popup chooses the available side and vertical direction, shrinks to fit the viewport, and scales its contents when narrower than the normal popup width. Inside the overlay, the popup fills the whole iframe instead of using the toolbar popup's fixed 24rem × 32rem size, so the tab panels reach the bottom of the overlay. The launcher is removed when the selector is unavailable and closes on circle click, outside click, Escape, or navigation; there is no separate close-button bar. The popup page and launcher icon are listed as web-accessible resources. The selected extension language is also sent as `responseLanguage` with each desktop AI request.

Hovering the launcher for 0.2 seconds reveals three 44px actions: **+**, **Summarize page**, and **Extract chapter characters**. They hide after 0.3 seconds away and appear on keyboard focus. Summarize and Extract explain when AI pairing/model/effort settings are missing. Action buttons have localized tooltips.

The single **+** starts a disposable text picker: click a word or drag a phrase, then choose **Keyword**, **Alias**, or **Version** in an icon-button panel above the selected text (clamped to the viewport). The panel embeds `popup.html?view=selection`, asks for a novel if detection cannot resolve one, and offers **Use AI**, on by default. Without a configured desktop client, it explains how to configure AI and continues manually. Alias and Version require a parent keyword from a debounced fuzzy searchable dropdown; it reads the novel's local view (pulling the novel first when the device has no copy), including alias names in matching. Changing the novel clears the parent.

Continuing opens the corresponding full-page form, seeded with selected text and the chosen novel/parent. AI uses up to 1,500 nearby characters on either side via the hidden `aiContext` parameter, then suggests description, category and nature in the extension language. Alias/version descriptions retain their parent note. Guests cannot create entries. Escape, outside click, close and disposal clear selection guards and iframe message listeners; the launcher accepts chooser messages only from its own iframe window and extension origin. Temporary page copy-protection overrides exist only while selecting.

Novel and keyword names are translated (`nameAr`/`nameEn`, novels also `descriptionAr`/`descriptionEn`), and the extension shows only the UI language's fields: an English UI lists and highlights only novels and keywords that have English names, and hides the rest. Requests carry the UI language as `Accept-Language` so the API filters online lists. The novel catalogue and downloads fetch both languages, and every local read filters by the current one, so switching language works offline. Forms edit and create the current language's name and description only; **Add novel** on a page whose slug an existing novel already has fills that novel's missing translation. Page highlighting matches the UI language's names and re-runs when the language changes. Local data and queued writes from before the change were moved to the Arabic fields, like the backend migration. Alias name script detection uses letters only, so Arabic-Indic digits alone do not count as an Arabic name.

Create, edit and delete forms occupy the entire content region beneath the navbar. The novel selector, warnings and tab controls are hidden while a form is open. Navbar **Back** closes the form and restores its originating page and selected tab. `components/form-page.tsx` preserves underlying page state while rendering the form through a shared portal.

**Extract chapter characters** places a panel at the start of the chapter content (the same content root highlighting uses). It embeds the extension page `popup.html?view=extract`, which resizes the panel through `postMessage` (the panel accepts messages only from its own frame). The page detects the novel, or asks the reader to choose one, reads up to 120,000 characters of chapter text from the content script (skipping scripts, hidden elements, and extension markup), and sends it with every category and nature description and the novel's known character and alias names to the desktop client. The answer becomes a table of editable **Name** and **Description** text fields, **Category**, **Nature**, and **Parent** selects (Parent searches every character of the novel, including alias names, with fuzzy matching), and per-row **New**, **Alias**, **Version**, and **Ignore** buttons. Names the novel already has are dropped. When the AI suspects a new name is another name (`alias`) or a later form (`version`) of a known character or of another row, it returns that parent: the row preselects it in **Parent**, shows a localized “AI: probably …” note, and fills the matching **Alias** or **Version** button while making **New** secondary. A suggested parent that is another row links up as soon as that row is added (its client ID is known at once); choosing or clearing the parent by hand stops applying the suggestion. **New** creates the character; **Alias** and **Version** are enabled once a parent is selected, and add the row under that parent with the same parent note as above (a version starts at the detected chapter). **Ignore** removes the row. Saves go through the offline-first mutation hooks and refresh the page's highlights. Navigation or the panel's **Close** button removes it.

Every novel has an optional **context** (genre, setting, power system, premise, main characters, tone), editable in the novel form. Keyword suggestions, chapter extractions and image generation add it to their prompts. When it is empty, the first of these AI actions asks the desktop client to research the novel with web search (`ensureNovelContext` in `src/lib/desktop-client/novel-context.ts`), saves the answer through `PUT /api/user/novels/:id/context`, and updates the downloaded and catalogue copies; a failed or offline research continues without context. Readers can fill a missing context; only moderators (roles with `user:moderate`) and the dashboard can change an existing one, so the form locks the field for other roles.

The keyword, alias and version forms have a **Generate image** button (`src/components/generate-image-button.tsx`). It reads the chapter open in the active tab, keeps the passages that mention the entry's name or aliases, adds its description, category, the novel context and the reader's image prompt, and asks the desktop client to draw one image with Codex. The result becomes the form's selected image file; saving queues it with the change, and the runner uploads it first through `POST /api/user/files/upload` (with a client file ID) to the backend's image storage (imgbb). The button works from the toolbar popup and the launcher popup; the background accepts desktop jobs from tabs and from extension pages.

All AI answers (summaries, suggestions, and extractions) are written in the extension language. Every prompt carries an explicit language rule, and when the returned descriptions are mostly in the other script (Arabic vs Latin letters), the request is repeated once with a correction.

Character and replacement searches tolerate small spelling mistakes and transposed letters while retaining partial-text matching. Character search includes alias names (their Arabic and English translations too) and version descriptions; replacement search includes both From and To. Searches run over the novel's local view, online and offline. Add character and Add alias prefill Name from the trimmed search; Add replacement prefills From. Versions have no separate name, so Add version prefills Description. Existing edit forms keep their saved values.

## Main areas

- `src/entrypoints/` contains background and content scripts, popup screens, and options UI. The popup uses React Router, Mantine, Jotai, and TanStack Query. Popup and options entries share `popup/render.tsx`, with one React root per page. The options page and embedded popup fill their viewport; the browser toolbar popup stays 24rem × 32rem.
- `src/components/`, `src/hooks/`, `src/store/`, and `src/utils/` contain shared presentation, state, and page logic.
- `src/styles/theme.ts` and `src/styles/global.css` apply the website's visual identity (see the website's `design-system/MASTER.md`) to every extension page: Ink & Iris neutrals, a violet `brand` primary (`#6554c0`) that becomes pale iris (`#b5a8f5`) with dark ink at night, neutral utility icons and semantic success/error/warning colors, Inter UI and headings, and IBM Plex Sans Arabic for Arabic. Lucide is the shared outline icon family at 1.75 stroke weight. Reader-defined keyword colors stay independent of the brand. Existing logo/icon assets are retained until the owner provides the new logo. Fonts are self-hosted through `@fontsource` packages, so extension pages make no remote font requests. In-page surfaces (launcher, keyword tooltip, selection hint, AI summary card) share `src/styles/palette.ts` through `contentThemeCss` for shadow DOM; tooltip content CSS mirrors the same palette. These surfaces honor the system appearance; extension pages honor the saved theme.
- `src/api/generated/` contains Orval output from the backend OpenAPI spec. `orval.config.ts` writes endpoint functions, React Query hooks, and schemas; `src/api/axios-instance.ts` configures the Axios transport, and `src/api/client-compat.ts` adds `X-Client-Version: extension/<version>` to every request. When the API answers 426 Upgrade Required, it asks the store for an update (hourly at most) and reloads into it; in development it warns about responses carrying a `Deprecation` header. See [API and data compatibility](compatibility.md). The output is committed so CI can typecheck and build without a backend; regenerate and commit it whenever the backend API changes. It covers only the reader API under `/api/user`: the config excludes the dashboard's `Admin: …` tags, drops the `ApiUser` prefix from operation IDs so generated names stay stable (`getNovelsById`), and cleans stale files.
- `src/lib/offline/` is the local-first engine (see [Account and synchronization](#account-and-synchronization)): the Dexie database `storylens` (`db.ts`), the outbox (`outbox.ts`), pure projections (`projection.ts`, `rules/`), views (`views.ts`), snapshot writers (`snapshot.ts`), the background runner (`sync/`), and the UI hooks (`hooks.ts`).
- `src/i18n/messages/` holds extracted application translations. `public/_locales/` holds browser manifest messages. The content script's tooltip has its own localized strings and reads locale from extension storage.

`wxt.config.ts` declares extension permissions, host permissions, React and icon modules, and an API URL fallback. Set `WXT_API_URL` to the running backend and `WXT_WEBSITE_URL` to the website origin serving account pages when developing locally; see the port caveat in [Development](development.md). Build and distribution targets are in the extension `Makefile` and `package.json`.

See the [extension instructions](../apps/extension/AGENTS.md) for code conventions and offline change requirements. The [extension README](../apps/extension/README.md) has submodule commands.

## Account and synchronization

The popup creates a guest account on first open and stores the session in `browser.storage.local` (`storylens-auth`). Sign-in, registration, profile edits, email and password changes, and sign-out live on the website's `/{locale}/profile/` pages, not in the popup: browser password managers such as Apple Passwords cannot fill forms on `chrome-extension://` pages. The popup's profile button opens that page in a new tab.

The `website-bridge` content script runs only on the `WXT_WEBSITE_URL` origin (default `http://localhost:3000` in development and `https://storylens.iscoded.com` in production builds). The profile button and the settings website, privacy, and terms links use the same origin through `websitePageUrl`. It answers `window.postMessage` requests on the `storylens-account` channel: `get` returns the stored session, `set` validates and stores a session from the page, and `clear` removes it. It also pushes storage changes to the page. Its protocol lives in `src/lib/website/account-bridge.ts` and must match the website's `src/lib/account/bridge.ts`. Open extension pages follow `storylens-auth` changes through `useAuthInit`. After sign-out, the next popup open creates a fresh guest, as before.

The stored user carries `isGuest`, its `role` and the role's `permissions` from `/api/user/auth/me`. `userAccessAtom` reduces them to an access level for the UI: guest, reader, or moderator (the role holds `user:moderate`). Per-row edit rights mirror the API in `src/lib/auth/permissions.ts`: keywords and replacements are changed by their creator or a moderator; aliases and versions by their own creator, the parent keyword's creator, or a moderator (decision D12). Cards a reader may not change open no form and explain who can. A stored session that no longer parses but still has a token reloads the user from `/auth/me` instead of becoming a guest.

### Offline-first engine

Every screen reads a **view** and every change goes through the **outbox**, online or offline; being online only changes how soon a change is sent.

- **Snapshot:** tables in the IndexedDB database `storylens` holding the rows the server last returned (novels, keywords, aliases, versions, replacements, categories, natures, chapter biases). Only pulls and push outcomes write them, inside the runner's lock.
- **Outbox:** the `mutations` table. `enqueue()` is the only writer from the UI: in one transaction it checks the signed-in account and the per-row permissions, validates against mirrors of the server's rules (unique names per language, version order, protected base versions, lookups in use), keeps only the fields the form changed (with the values the form started from and the row's `updatedAt`), folds the change into an unsent one for the same entity, and records dependencies. IDs are client UUIDs, so nothing is remapped when a create syncs. Once a form closes as saved, the change survives closing the popup, a worker restart and going offline.
- **Views:** the snapshot with the signed-in account's unresolved changes applied (`projection.ts`, pure): a new keyword gets its base version, deletes cascade, versions auto-close, replacement chains rewrite, and categories and natures are embedded from the projected lookups. Page highlighting reads the same view through the background (content scripts never open the database). Popups refresh when another context writes the database (Dexie `storagemutated`, with a change-counter check as fallback).
- **Runner** (`sync/runner.ts`, background only): under the `storylens-sync` Web Lock it recovers expired leases, checks the session and the API's sync protocol (`GET /api/user/sync/protocol`, version 2), then sends the outbox one change at a time, in order per entity and after the creates they depend on, each request with a 20 s timeout and the change's own account token. Outcomes follow the API's codes: stale writes (409 `STALE_WRITE`) merge per field automatically and conflict only when both sides changed the same field; deletes win and a 404 on delete counts as done; duplicates, missing parents, rule and permission refusals need the reader; 401 and 426 pause the runner without counting attempts; network errors, 5xx and 429 back off (5 s doubling to 15 min, jittered, honouring `Retry-After`) and never exhaust a change. Runs are triggered by `syncKick` after saves and on popup open, a 5-minute alarm (created only when missing), a retry alarm at the next due change, browser start, updates, the worker's `online` event and sign-in changes. Changes made while signed in as another account are held and never sent with this account's token.
- **Pulls** (`sync/pull.ts`): lookups and downloaded (pinned) novels refresh when older than 10 minutes (all of them on **Sync now**), cached novels when a page or the popup uses them (the page gets local data at once and refreshes when the pull lands), the catalogue on popup open when older than 30 minutes. Every list is fetched to its last page in both languages. After a first full pull, units refresh from the API's change feeds (delta pulls from a cursor), with a full pull again for an expired cursor or once a week. Pulls replace server rows in one transaction and never drop local changes; a pending update of a row the server deleted becomes a `deleted` conflict. Tabs showing a changed novel re-run highlighting.

The navbar's sync button is always visible: its icon shows synced, pending (with a count), sending, offline, paused or needs attention, and its popover shows the last sync time, counts, pauses (**Sign in again**, **Update required**, "Sync paused until Story Lens updates" when the API is older than this build) and **Sync now**. The toolbar badge counts the account's unresolved changes (orange pending, red needs attention, grey `!` offline).

The **Sync status** page (from the popover, card badges or toasts) lists changes that need the reader, grouped as **Needs attention**, **Made while signed in as …** and **Waiting to sync**. Stale conflicts show a table of each field's yours, theirs and original values with **Keep mine** / **Use theirs** per field or for all; deleted rows can be discarded or created again; duplicates and refused rules can be edited inline and resent, and a duplicate keyword offers **Show existing** (the coloring tab searched to its name); discarding lists and drops the changes made under the item, and focus moves to the next card. Conflict tables show category and nature names, chapters and image thumbnails. Every card in the coloring, replacing and settings lists shows its sync state ("Pending", or "Needs attention", which opens the page), and deleting a keyword created offline says how many unsent changes under it go too.

Downloads go through the background (`downloadNovel`): it pins the novel and pulls it under the lock. Removing a download with unsynced changes opens a dialog (**Sync now**, **Discard changes and remove**, **Cancel**); a novel removed on the server shows a banner offering to remove it. Novels, slugs, website selectors and chapter biases are online-only (decision D6): their actions are disabled offline with an explanation, and after an online save the runner pulls the novel again. Images attached or generated in character forms are kept on the device (up to 10 MB each) and uploaded with the change; page tooltips show them once uploaded. If IndexedDB cannot be opened (for example Firefox with site data blocked), the popup shows a banner, lists and page highlighting read straight from the API, and edits are refused with that reason (they could not be kept).

Updating from 3.2.x deletes the old `storylens-offline` database and `storylens-sync-state` pool without reading them: novels must be downloaded again, and changes that had not synced before the update are lost (decisions D13, D14).

Run the extension tests with `bun run test` (or `make test`) from `apps/extension`; they use a fake browser, `fake-indexeddb` and an in-memory API that follows the sync contract (`test/helpers/`), and `test/ui/` renders components with happy-dom and Testing Library.

## Usage analytics

The extension sends pseudonymous Google Analytics 4 events through the Measurement Protocol from the background service worker; Manifest V3 forbids remotely hosted code, so `gtag.js` is not used. Popup and content scripts call `trackEvent()` (`src/lib/analytics/client.ts`), which forwards a typed `trackAnalyticsEvent` message to `src/lib/analytics/background.ts`. The background attaches a random client ID (`storylens-analytics-client-id` in extension-local storage), a 30-minute session ID in session storage, and the extension version, then posts to `https://www.google-analytics.com/mp/collect` (a declared host permission). Development builds use GA's debug endpoint and log validation results.

Analytics is disabled unless `WXT_GA_MEASUREMENT_ID` and `WXT_GA_API_SECRET` are set at build time. **Settings → General → Anonymous usage analytics** defaults to on and is saved as `storylens-analytics-enabled`. Events never include page text, titles, full URLs, or account data; a supported novel-page event includes the reading site's hostname. The event catalog and the rules for adding or removing events live in the [extension instructions](../apps/extension/AGENTS.md#analytics-events). Store copy and disclosure drafts in both languages live in [the extension store directory](../apps/extension/store/).

## Chrome Web Store release

[Listing metadata](../apps/extension/CHROMEWEBSTORE.md) tracks store text, permission explanations and asset status. The umbrella [demonstration assets](chrome-store/README.md) use the actual production extension with an original sample chapter and isolated local data; fixtures are outside the extension build.

Bump `version` in `apps/extension/package.json`, commit, and push a matching `v<version>` tag, or run the **Publish to Chrome Web Store** workflow manually. `.github/workflows/publish-chrome.yml` runs `make install`, `make typecheck`, `make release-chrome`, and `make submit-chrome`, then sends an `extension-submitted` `repository_dispatch` event with the version to `storylens-backend`. That repository's **Set Review_Version** workflow records the version on the server. The backend deploys itself after the store publishes that version; see [Backend](backend.md#deployment-and-review-version).

For first-time setup on a new account, follow the [publishing runbook](publishing.md). The first store listing must be created manually. The workflow job uses the repository's `production` environment. It reads the public extension ID from that environment's variable `CHROME_EXTENSION_ID`, and needs these environment secrets: `CHROME_CLIENT_ID`, `CHROME_CLIENT_SECRET`, and `CHROME_REFRESH_TOKEN` (an OAuth refresh token for the `https://www.googleapis.com/auth/chromewebstore` scope, which you can get from the OAuth Playground with a Web application client), plus `BACKEND_DISPATCH_TOKEN`, a fine-grained token with Contents read and write access to `storylens-backend`, which the repository dispatch API requires. The SSH deploy secrets live in the backend repository.

Settings → General includes Website, Privacy Policy, and Terms of Use links on `storylens.iscoded.com`, using the selected English/Arabic locale.
