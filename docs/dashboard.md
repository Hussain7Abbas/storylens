# Story Lens dashboard

[Documentation index](intro.md) · [Backend permissions](backend.md#portals-roles-and-permissions)

`apps/dashboard` is the independent public `storylens-dashboard` repository, the fifth submodule. It is a Vite + React single-page app for the backend's dashboard API (`/api/admin`), served as static files by Nginx at [storylens-dashboard.iscoded.com](https://storylens-dashboard.iscoded.com). Source uses PolyForm Noncommercial 1.0.0.

## What it manages

- **Overview:** reader, guest and dashboard account counts, new accounts this week, catalogue totals, newest accounts and novels, plus a **Lenses** card (pending requests, sales, lenses sold and gifted, and AI cost) for roles that can read the billing summary.
- **Users:** search and filter every account by access and role; create verified accounts with reader access, dashboard access (the only way to grant it), or both, each with its own role; edit name, username, email, the shared password, and each access and role; sign a user out everywhere; delete users. Enabling reader access defaults to the Reader role even when Guest appears first in the API list. The API refuses to change your own dashboard access or role, delete yourself, or remove the last super admin.
- **Roles:** dashboard and reader roles with user and permission counts. The role editor lists every permission of the role's portal grouped by resource, with method, route and description, filter, per-group toggles and select all/clear. Super Admin is read-only because it always holds every dashboard permission; system roles can't be deleted, nor can roles that still have users.
- **Novels:** search, sort, create, edit (Arabic and English names and descriptions, cover upload, slugs, AI context) and delete, with keyword, chapter and replacement counts. Clicking a row opens the novel's profile.
- **Novel profile** (`/novels/:id`): the novel's cover, names, descriptions, slugs, counts and AI context, followed by **Characters** (default) and **Chapters** tabs. Characters lists keywords. An AR/EN switch shows the keywords named in that language (by the name's script). Columns: image, character, languages supported (Ar, En), category, nature, description, match (full word or partial), added by, and actions: edit (names, matching and the base version's category, nature, description and image), delete, add alias and add version, each in a modal, plus **New keyword** (the same form; it creates the keyword with its base version), with a confirmation before deleting. Keyword and alias forms show an Arabic character variant switch below Full word match when either name contains Arabic letters; it defaults on and distinguishes ا/أ/إ/آ/ٱ when off. Versions (when there is more than one) and aliases are nested under their keyword as in the extension, showing the keyword's values in italics where they inherit them; the base version can't be deleted. Aliases are named per language like keywords (the API removed the old single `name`). The keyword and alias forms are split into **AR** and **EN** tabs, opening on the table's language; each tab holds that language's **Name** and **Description** plus the shared style fields, and the other language's tab begins with an optional **Link**: a searchable picker of the entry already named in that language and not in the table's, which saving merges into this one (`translationKeywordId`/`translationAliasId`; see the [backend guide](backend.md#sync-api)). A keyword form offers the novel's other keywords, an alias form the same keyword's other aliases. Candidates must agree with any stored name in the linked language (`KeywordPicker.targetName`), so bilingual entries cannot select a conflicting translation. Both forms require at least one name in the actual saved payload even with a link, because the API checks names before merging. Choosing one fills that tab's name (then read-only, since it belongs to the linked entry until the merge) and fills the linked language’s description and overwrites the form's category, nature and image, because the merged row goes; the request carries the link rather than that name. Switch the AR/EN control to put **Link** on the other tab. Above the table are one filter per column and a full search across names, aliases, descriptions, categories, natures and creators (fuzzy for names; filters are kept in the URL).
- **Match translations:** for one novel, lists keywords named in only Arabic or only English (50 per page). A row's language comes from its name's script, not its column: older keywords keep English names in `nameAr`, so those rows ask for the Arabic name, and saving moves the English name to `nameEn`. The page pairs with the Story Lens desktop client (port, prefilled with the client's default 43127, and pairing token from the client's Settings tab, saved in this browser), which suggests each missing name and whether the keyword already exists in the other language. Suggestions run only when asked: **Suggest page** (then **Re-suggest page**) sends the page's rows, and while it runs the button becomes **Cancel suggesting**, which aborts the request so the desktop client stops the model; changing page or novel also cancels. Re-suggesting replaces earlier AI-filled drafts while preserving rows the admin edited. Each row has an editable translation and Link / Alias of / Version of pickers that fuzzy-search the novel in both languages (typos and Arabic spelling variants match). **Link** offers every keyword and every alias (labelled “Alias of …”), because a row may be the translation of another character's alias; linking to an alias makes the row that alias's name in the other language, moves the row's image, category and nature onto it where the alias has none (or where the row's are newer), and removes the row. **Alias of** and **Version of** offer main keywords only (still found by their aliases). Versions are never offered; choosing one disables the others. Linking checks that the target has no different name in the row's language. **Save** applies the translation or the chosen relation, **Ignore** hides the row until reload, and checked rows can be saved or ignored together. Selections belong to the current page, so changing page asks first. Chrome may ask to let the dashboard reach apps on the device.
- **Users → lenses:** each reader shows their lens balance; **Gift lenses** (with an optional note the reader sees), **Adjust** (signed, with a reason only the dashboard shows) and **History** (the reader's ledger) open in dialogs. Guests and dashboard-only accounts have no lenses.
- **Billing requests** (`/billing-requests`, with a pending count in the sidebar): readers' lens requests, filtered by status (pending by default) and searched by email or contact. Each row shows the reader's email (current and at request time), the WhatsApp or Telegram contact with a chat link, the lenses, the price and total quoted at request time, and the reader's balance. **Approve** credits the lenses once and emails the reader; **Reject** needs a reason, which is emailed.
- **Settings** (`/settings`, `?tab=configs|ai|categories|natures`; `/configs` and `/ai-pricing` redirect here): **Configs** adds, edits and deletes every runtime key–value config (`Review_Version`, the `Lens_*` and `AI_*` billing keys, with hints and validation for the known ones). **AI** turns Story Lens Cloud on or off, chooses the **Text model** and **Image model** from searchable lists loaded from OpenRouter's catalogue (`GET /api/admin/ai-models/`, cached 10 minutes, **Refresh** reloads it) and saves them as the `AI_Text_Model` and `AI_Image_Model` configs. A selected model shows its prices (per million input and output tokens, per request, per image), and a table estimates each feature's cost per action with that model (typical token counts, OpenRouter's ~5.5% fee, Exa search for novel research) against what its lenses earn at the current lens price. A feature that would lose money is marked, the card says how far the lens price (or that feature's lenses) must rise to break even and to keep a 1.5× margin, and saving a money-losing model asks for confirmation. The table’s final Actions column has a pencil for each feature; it opens the feature’s names, lenses, availability and prompt/output limits in a modal. Feature forms are no longer listed below the models card.
- **Account:** own display name, username and password.

There is no registration page. `make backend-seed-dashboard-admin` gives `DASHBOARD_ADMIN_EMAIL` super-admin dashboard access: if a reader account already uses that email it keeps its password and reader access, so the same sign-in works in the extension and here; otherwise a dashboard-only account is created from `DASHBOARD_ADMIN_USERNAME` and `DASHBOARD_ADMIN_PASSWORD`. Everyone else gets dashboard access on the Users page.

Navigation, pages and buttons follow the signed-in role's permissions (`can()` in `src/lib/auth.tsx`, keys in `src/lib/permissions.ts`); the API enforces them regardless. A role without the overview permission lands on its first allowed page.

Novel covers and keyword, alias and version images share a 100px drag-and-drop uploader (`components/ui/image-field.tsx`). It has a centered upload icon, click or keyboard selection, hover and accepted/rejected drag feedback, preview and a separate delete button. Choose one image up to 8 MB; uploading requires the file-upload permission. Uploads start immediately, while saving the form persists the image reference or its removal. Replacement, deletion and saving are disabled during upload; closing the form aborts it, and failures keep the previous image. `tests/image-upload.spec.ts` verifies these controls across the four forms on desktop and mobile.

## Design

The dashboard uses the website's Ink & Iris identity: the same light/dark tokens, Inter, Lucide icons at 1.75 stroke, iris primary actions and the Lensbook logo. `apps/dashboard/design-system/MASTER.md` records how the admin layout applies it; the vendored UI UX Pro Max skill supplied the minimal, dense dashboard structure, while its palette and fonts were rejected for Ink & Iris. Light, dark and system themes, reduced motion, keyboard focus, 44px coarse-pointer targets and no page-level horizontal scroll at phone widths are covered.

Lens coins across the dashboard retain their original static full/small/mono SVG. Three surrounding CSS sparkles brighten at 300 ms offsets, each repeating every 900 ms, using theme iris or `currentColor` for mono. Hover/focus on a containing control pauses them; reduced motion and forced colors hide them. The independent `src/lib/lens-coin/LensCoinSparkles.tsx` and global styles mirror the canonical [branding source](branding/README.md#lens-coin), with no player or timers. `tests/lens-motion.spec.ts` verifies staggered lighting, static artwork and reduced-motion changes.

## Development and checks

`make dev-dashboard` serves it at http://localhost:3040 against `VITE_API_URL`. `make dashboard-orval` regenerates `src/api/generated/` from a running backend (`ORVAL_API_URL`); only `Admin: …` tags are generated. `make dashboard-typecheck`, `dashboard-lint`, `build-dashboard` and `dashboard-test` (Playwright + axe on Chromium desktop and mobile with a mocked API; `CHROMIUM_PATH` selects a preinstalled browser) are the checks.

Before local development, copy `apps/dashboard/.env.example` to `apps/dashboard/.env` and set `VITE_API_URL` to the local backend origin (the example uses `http://localhost:3030`; match the backend's `PORT`). Restart the dashboard dev server after changing its environment. Without `VITE_API_URL`, the dashboard falls back to the production API, so locally seeded `DASHBOARD_ADMIN_*` credentials will not authenticate there. `.env.production` selects the production API for production builds.

For a live browser check, start a **disposable** local PostgreSQL database, apply the backend migrations, and seed it with `NODE_ENV=development` and test-only `DASHBOARD_ADMIN_*` credentials. Start the backend against that database, then build the dashboard with `VITE_API_URL` set to the loopback backend and start `bun run preview`. Run `STORYLENS_E2E_API_URL=<same loopback API> STORYLENS_E2E_ADMIN_EMAIL=<seed email> STORYLENS_E2E_ADMIN_PASSWORD=<seed password> bun run test:e2e -- --project=chromium tests/live-api.spec.ts`. The test uses real routes and checks browser sign-in, dual portal access, novel and keyword writes, translation saving, and the outdated-client response. It is skipped in the ordinary mocked suite. Keep it pointed at an isolated database because it creates test records.

## Production

- DNS: Cloudflare A record `storylens-dashboard.iscoded.com`, proxied, to the same server as the website (`178.105.43.174`), created with `flarectl` like the website's.
- Server: `ssh raseen`, checkout `/srv/storylens-dashboard` on `main`, releases in `/var/www/storylens-dashboard/releases` with a `current` symlink.
- `make sync` (as root in the checkout) pulls `main`, installs with Bun, builds with the Node LTS in `/opt/storylens-node/bin`, activates the release, installs `deploy/nginx/storylens-dashboard.iscoded.com.conf`, requests a Let's Encrypt certificate through `deploy/nginx/bootstrap.conf` on the first run, checks `/login` and rolls back on failure. The five newest releases are kept.
- `Deploy production` (`.github/workflows/deploy.yml`) runs when the backend dispatches `backend-deployed`, or by manual dispatch on `main`. The backend's review-version watcher sends that event only after its own `make sync` succeeds, so the dashboard follows each backend release; see [Backend](backend.md#deployment-and-review-version). Pushes to `main` do not deploy, and it runs no checks. It sends `main`'s SHA over SSH with the `production` environment secrets `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_SSH_KEY` and `DEPLOY_SSH_PASSPHRASE`; the key is a dedicated passphrase-protected ed25519 key, and the workflow decrypts it on the runner. On the server, `root`'s `authorized_keys` restricts that key to `command="/usr/local/lib/storylens/dashboard-ci-ssh.sh",restrict`. That wrapper is installed from `deploy/ci-ssh.sh`. It validates main ancestry, refuses dirty checkouts, locks, checks out the exact commit and runs `make deploy`. Updating the installed wrapper is separate from publishing the dashboard.
- Nginx sends a strict CSP (scripts and styles from self; API calls only to `https://storylens-api.iscoded.com`), `noindex`, long-lived caching for hashed `/assets/`, and falls back to `index.html` for client routes.
- The backend must be deployed with the role and access migrations and `DASHBOARD_ADMIN_*` set, then `make seed-dashboard-admin` run once in `/srv/storylens-backend`.

Keyword/alias descriptions save independent `descriptionAr`/`descriptionEn` fields (keywords on the base version); the table and nested rows show the selected language. A version form edits both descriptions explicitly. Translation links retain both languages, and clearing one description keeps the other. Older API responses use their shared description only in the language identified by its script.

The AI settings also list `chapter_cover` pricing after the chapter-cover migration. It uses the image model like `character_image`, with a separate estimate for the longer chapter scene brief and independent editable lens price and limits.

The `chapter_context` text feature appears in Settings → AI with editable lens pricing and a structured-output cost estimate (15,000 typical input / 5,000 output tokens). Chapter covers remain an image feature.

Settings → AI also saves **Reasoning effort**, **Reasoning token allowance** and **Image quality** through `AI_Reasoning_Effort`, `AI_Reasoning_Token_Allowance` and `AI_Image_Quality`. Effort and quality default to **Auto (model default)**; the allowance defaults to 4,096 additional completion tokens (0–32,768) above the feature’s answer/brief cap. Reasoning and the visible answer share the combined budget. The controls use OpenRouter capability metadata, exclude off for mandatory-thinking models, and show Auto when a saved level is unsupported after a model change. Changes apply to the next Cloud action, including image briefs and chapter covers; local desktop settings remain separate. Existing config-save permissions gate editing.

Estimates include the full extra reasoning allowance when thinking is enabled, making them conservative with respect to that allowance. Image price metadata lacks quality-specific token counts: Auto/medium retain the labelled baseline assumption, while other supported qualities show unavailable image estimates and no suggested image lens price. Use recorded costs after testing that quality; the 30-day averages mix previous models/settings. Saving an estimable setting that would lose money asks for confirmation, as model changes do.


Settings → AI includes **Available lens balance**, stored as the `AI_Lens_Balance` Config (0–999,999,999 whole lenses, absent means zero). The dollar converter uses `Lens_Price_USD` and exact integer micro-dollars, rounding fractional lenses down. Saving replaces the remaining stock; it does not add a top-up or fetch the OpenRouter balance. Approved sales and dashboard gifts deduct stock atomically on the backend; reader AI spending, refunds, trial gifts and corrections leave it unchanged. Gift and sale dialogs validate against the available stock when Config read access is present; the API always enforces it. Config permissions gate the balance card and edits. Set the initial stock before approving sales or issuing gifts. Balance edits include `baseUpdatedAt`; a concurrent deduction keeps the draft visible and requires **Reload balance** before saving again.

The text/image model picker is an editable combobox with search inside the selected-value control, Arrow keys, Enter and Escape. Feature editing is opened by a pencil in the cost table’s final **Actions** column and saves the existing pricing form in a modal; roles without model-list permission still see the feature table and can edit when allowed by pricing permissions.

Novel profiles have **Characters** (default) and **Chapters** tabs (`?tab=chapters`, with keyboard navigation). Chapters paginate the admin chapter endpoint and show artwork thumbnails, number, name and updated date. Opening a row fetches the scoped detail endpoint and shows the full background image with structured chapter context beneath it, including observations and lasting changes. Context is absent from chapter list responses. New chapter-list and chapter-detail permissions independently gate these views; private generation reservations are never returned.


Keyword and alias create/edit dialogs include a collapsed **Advance** section with **Main Theme Color**: a hex field, native color picker and **Use inherited color** reset. Save nullable `mainThemeColor` through the existing keyword/alias API; reject non-six-digit hex colors. It overrides the word’s category color and is shared with readers; blank aliases inherit their keyword’s override first. Opening or switching language tabs preserves the draft, and existing edit permissions still apply. Backend deployment needs the additive `main_theme_color` migration.


Settings → **Categories** (`?tab=categories`) and **Natures** (`?tab=natures`) use `components/settings/lookup-settings.tsx` to list/add/edit/delete shared lookups. Forms edit English/Arabic names (at least one), hex color and nullable AI guidance (up to 1,000 characters); category forms also retain None, Sparkles, Heat, Shaking, Glitching and Glare, nullable Heat/Sparkles tint with **Use word color**, and **Switch position with nature**. `lookup-color-preview.tsx` shows live English/Arabic samples on fixed Ink & Iris light/dark surfaces, plus WCAG contrast readings. Category samples follow the position switch; nature samples show both marker and swapped text. Preview colors intentionally preserve user choices, including low contrast, and remain visible in forced colors; surrounding labels and guidance retain accessible contrast. These fixed evaluation surfaces are an exception to theme-relative component colors. Each GET/POST/PUT/DELETE action uses its corresponding admin route permission; nature-only read access also exposes Settings. Creates send a stable UUID for retry safety. PUT includes `baseUpdatedAt`; errors retain drafts and reopening loads the latest row. Category and nature deletion share a centered confirmation dialog with a same-type replacement selector (excluding the source); used rows cannot be deleted without one. `tests/lookup-settings.spec.ts` verifies replacement submission and viewport centering for both types on desktop and mobile. Category VFX applies when a word has no explicit effect; the legacy `effect` field is never edited. The existing category VFX/swap migrations remain required; this editor adds no migration. Browser coverage lives in `tests/category-vfx.spec.ts` and `tests/lookup-settings.spec.ts`.

Glare is stored as `GLARE` and has no tint picker. It needs backend migration `20261017214616_glare_word_vfx`; reader and admin clients include the new WordVfx enum value.

Category editing in Settings → Categories also exposes **Switch position with nature**, default false. Save `switchPositionWithNature` with the existing category update permission and revision precondition. Readers then use nature color for word text and category color for the circle, with explicit Main Theme Color overrides preserved. The backend needs migration `20261017215230_category_swap_colors`.

Keyword, alias and version forms include an initially collapsed **Image Prompt** section with a 100px editable preview, a bottom gradient and Expand control, and a copy icon at the textarea’s top end. A keyword’s prompt belongs to its base version. The text is shared across AR/EN tabs, saved alongside its image and carried with translation image links. It can be edited here and reused by extension image regeneration; the dashboard has no AI image-generation action.

Lens request minimum/maximum Config keys are retained only for compatibility; their hints explain that the request range is now fixed at 500–2,147,483,647. Price arithmetic uses exact BigInt intermediates for large quantities.

Settings → AI includes **AI prompts** (`components/settings/ai-prompts.tsx`): Keyword generation, Character images, Chapter covers, Chapter context and Page summary, each in a collapsible editor with Save prompt, Reset to default and Reload saved prompt. `GET /api/admin/ai-instructions/` supplies effective text, defaults, a 20,000-character cap and per-key revisions. Read permission alone exposes the AI tab; existing Config PUT permission enables editing. Save the matching `AI_Keyword_Prompt`/`AI_Image_Prompt`/`AI_Chapter_Cover_Prompt`/`AI_Chapter_Context_Prompt`/`AI_Page_Summary_Prompt` key with `baseUpdatedAt`; blank restores the default and resets remain drafts until saved. Preserve drafts on errors, and reload concurrent changes explicitly. The extension no longer exposes these template settings; Cloud and Desktop prompt construction reads the shared templates, while per-record saved image prompts remain independently editable. No database migration is needed. Browser coverage is in `tests/ai-prompts.spec.ts`.

Chapter context and Page summary use the same template read/save permissions, 20,000-character limit, reset/reload controls and revision checks as the image/keyword templates. Chapter-context instructions control extraction detail while the extension retains the JSON/schemaVersion and canonical identity contract. Summary instructions control content/style while the extension retains the selected output language, plain-text output, source cleaning and size checks. Changes apply to new generations; existing chapter contexts and summaries are not automatically regenerated.


Chapter-context instructions in Settings → AI now default to compact visual-only extraction. Migration `20261018040000_compact_visual_context` updates the shared template while retaining customized priorities. Current generation uses one nearest earlier chapter and a single bulk read only for returning elements; it never uses later chapters. Active absence expires at 10 chapters and tracks last seen only.
